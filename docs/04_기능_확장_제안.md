# 잇벤토리 (Eatventory) — 기능 확장 제안

작성: 이서준 (프로덕트 매니저)
기준: `docs/01_기획서.md` 3장의 우선순위 표, `docs/02`/`docs/03`의 화면·디자인 스펙, `src/` 실제 구현 코드(`src/pages/`, `src/context/AppContext.jsx`, `src/data/mock.js`, `src/utils/match.js`)

이 문서의 목적은 두 가지입니다. 첫째, 기획서 3장의 P0/P1/P2 표를 지금 코드 상태 기준으로 다시 채점합니다. 둘째, 기획서에 없던 새 기능을 "누가, 어떤 상황에서 불편한가"부터 시작해 발굴하고, 우선순위와 하지 않을 이유까지 포함해 정리합니다. 화려한 아이디어를 많이 나열하는 것보다 무엇을 먼저 하지 말아야 하는지 말하는 게 이 문서의 더 중요한 역할이라고 생각합니다.

---

## 1. 현재 구현 상태 요약

### P0 — 3개 전부 구현 완료

| 기능 | 상태 | 근거 |
|---|---|---|
| 재료 저장소 (냉장고/선반) | ✅ 구현됨 | `Fridge.jsx` + `AppContext`(`addIngredient`/`updateIngredient`/`removeIngredient`), 실온/냉장/냉동 탭·등록·수정·삭제 모두 동작 |

| 레시피 상세 보기 | ✅ 구현됨 | `RecipeDetail.jsx` — 보유/부족 재료 체크·X 아이콘 구분, 단계별 조리 순서 표시 |

### P1 — 4개 전부 구현됨 (일부는 기획서보다 더 나아감)

| 기능 | 상태 | 근거 |
|---|---|---|
| 재료 검색/필터 | ✅ 구현됨 | `Fridge.jsx`의 이름 검색 입력 + 카테고리 탭. 다만 `docs/02` 화면 1(홈)에 명시된 헤더 검색 아이콘은 홈 화면에는 없고 냉장고 화면에만 있음(사소한 편차, 기능 자체는 존재) |
| 유통기한 표시/임박 알림 | ✅ 구현됨 | `expiresInDays` 필드 + `fridgeTheme.js`의 D-day 배지(임박/곧임박/정상 3단계), `Home.jsx`에 "유통기한 임박 N개" 요약 표시 |
| 레시피 즐겨찾기 | ✅ 구현됨 | `AppContext.toggleFavorite` + `Favorites.jsx`, `RecipeCard`/`RecipeDetail` 양쪽에서 토글 가능 |
| 부족 재료 안내 | ✅ 구현됨 | `getRecipeMatch`의 `missing` 배열을 `RecipeCard`("○○ 없음")와 `RecipeDetail`(X 아이콘)에서 노출 |

### P2 — 3개 전부 미구현 (기획서 원안 그대로 유지)

| 기능 | 상태 |
|---|---|
| 재료 자동 인식(영수증/바코드) | ❌ 미구현 — OCR/바코드 인식 API 연동 필요, 백엔드 없는 현재 구조로는 불가 |
| 소셜 로그인/기기 간 동기화 | ❌ 미구현 — 계정·인증·서버 DB 필요 |
| 커뮤니티 레시피 공유 | ❌ 미구현 — 사용자 생성 콘텐츠 저장·조회·모더레이션 인프라 필요 |

### 기획서에 없던, 이미 구현된 것

- **라이트/다크 모드 토글** (`ThemeContext.jsx`): 기획서 3장에는 없던 항목이지만 이미 구현되어 있고, `localStorage`에 선택값을 저장하는 패턴이 이미 검증되어 있습니다. 이 패턴은 아래 3-③ 제안(데이터 영속화)의 근거가 됩니다.
- **냉장고 화면 실물 재해석(`docs/03` v2)**: 재료를 카드가 아닌 종류별 실루엣 "용기"(`IngredientVessel`)로 표현하는 디자인이 반영되어 있습니다.

### 구현 상태 기준 한 줄 평가

P0·P1은 사실상 다 끝났습니다. 다음 스프린트의 진짜 질문은 "P1을 더 다듬을지"가 아니라 "P2(계정·자동인식·커뮤니티) 중 하나를 시작할지, 아니면 P0/P1 사이에 있던 더 근본적인 빈틈(데이터가 새로고침하면 사라진다는 것)을 먼저 메울지"입니다. 저는 후자라고 판단합니다 — 아래 2장 참고.

## 3. 기능별 상세 설명

### A. 재료 데이터 영속화 (localStorage)

**시나리오**: 페르소나 B(살림하는 2인 이상 가구)가 냉장고 재료 10개를 공들여 입력했는데, 실수로 탭을 새로고침하거나 브라우저를 닫았다 열면 전부 사라집니다. 재고 관리가 목적인 사용자에게 "입력한 게 사라진다"는 것은 기능이 아무리 잘 만들어져 있어도 실사용을 포기하게 만드는 치명적 결함입니다.

- **임팩트**: 이 프로젝트의 핵심 미션(재료 낭비 방지)은 "며칠에 걸쳐 재고를 계속 확인"하는 반복 사용을 전제로 합니다. 세션이 끝나면 리셋되는 지금 구조에서는 그 반복 사용 자체가 성립하지 않습니다. 아래 C(소진/낭비 리포트)도 이 위에서만 의미가 있습니다.
- **난이도**: 매우 낮음. `ThemeContext.jsx`가 이미 `localStorage`에 값을 저장/복원하는 패턴을 증명해뒀습니다. `AppContext`의 `ingredients`/`favorites`도 같은 패턴(초기값을 `localStorage`에서 읽고, 변경 시마다 `setItem`)으로 확장하면 됩니다. 백엔드도, 새 라이브러리도 필요 없습니다.
- **우선순위**: 최우선. 이후 제안(C, D)이 여러 세션에 걸친 데이터를 다루는 순간 이 작업이 선행되어 있지 않으면 다시 만들어야 합니다.

### B. 유통기한 임박 재료 우선 반영 추천 정렬

**시나리오**: 페르소나 A(자취생)가 계란 유통기한이 하루 남았는데, 홈 화면의 "오늘 만들 수 있는 요리" 추천은 지금 단순히 "보유 재료 매칭 비율"로만 정렬되어 계란이 안 들어간 레시피가 먼저 뜰 수 있습니다. 정작 지금 가장 급하게 써야 할 재료를 추천이 무시하는 셈입니다.

- **임팩트**: 이 서비스의 존재 이유가 "재료를 안 버리게 하는 것"인데, 현재 로직은 D-day를 화면에 배지로만 보여줄 뿐 추천 알고리즘에는 전혀 반영하지 않습니다(`Home.jsx`의 정렬 기준은 `ownedCount/total`뿐). 이 간극을 메우는 게 신규 화면을 만드는 것보다 미션에 더 직접적으로 기여합니다.
- **난이도**: 매우 낮음. 새 데이터도, 새 UI도 필요 없습니다. `Home.jsx`/`RecipeList.jsx`의 정렬 함수에 "부족한 재료 수" 외에 "보유 재료 중 임박(`expiresInDays <= 3`) 재료가 이 레시피에 포함되는가"를 가중치로 추가하면 됩니다. 레시피 카드에 "유통기한 임박 재료 활용" 같은 작은 배지를 얹으면 체감 효과도 큽니다.
- **우선순위**: 최우선. 노력 대비 미션 기여도가 이 문서에서 가장 높은 항목입니다.

### C. 재료 소진/폐기 구분 기록 + 낭비 리포트

**시나리오**: 페르소나 B가 대파를 자꾸 사놓고 다 못 쓰고 버리는 걸 스스로도 잘 인지하지 못합니다. 지금 "삭제" 버튼은 다 먹고 지웠는지, 상해서 버렸는지 구분하지 않고 그냥 목록에서 없앨 뿐이라 앱이 "낭비를 줄여준다"는 걸 사용자가 체감할 방법이 없습니다.

- **임팩트**: `AddIngredientModal`의 "삭제"를 "다 먹었어요"/"버렸어요" 두 가지로 나누고, 그 기록을 누적해 홈이나 냉장고 화면에 "이번 달 버린 재료 3개(대파 2회, 우유 1회)" 같은 요약을 보여주면, 이 서비스가 유일하게 할 수 있는 "당신이 뭘 낭비하고 있는지 알려주는" 기능이 됩니다. 경쟁 서비스(만개의레시피, 해먹남녀, Supercook) 어디에도 없는 차별점이기도 합니다.
- **난이도**: 중간. `AppContext`에 소비 로그 배열을 추가하고, 삭제 플로우를 2단계 선택으로 바꾸고, 요약 UI를 새로 만들어야 합니다. 백엔드는 필요 없지만(A의 localStorage 확장으로 충분), 데이터 모델 변경과 새 UI가 함께 필요해 A/B보다는 공수가 큽니다.
- **우선순위**: P1. A가 선행되어야 로그가 의미를 가지므로 A 다음 순서로 배치합니다.

### D. 부족 재료 기반 장보기 리스트

**시나리오**: 페르소나 A가 레시피 3개를 훑어보며 "이건 대파가 없고, 저건 식용유가 없네" 하나씩 확인은 하지만, 정작 장을 보러 갈 때는 그 정보가 흩어져 있어 다시 기억을 더듬어야 합니다.

- **임팩트**: 레시피 상세/리스트에서 "장보기 리스트에 담기" 버튼으로 부족 재료를 모으고, 여러 레시피를 겹쳐 봐도 중복 없이 취합되는 리스트 화면 하나만 있으면 "추천받기 → 장보기 → 다시 등록" 흐름이 앱 안에서 닫힙니다. 지금은 부족 재료를 "보여주기"만 하고 "다음 행동"으로 연결하지 않는데, 이 기능이 그 연결을 만듭니다.
- **난이도**: 중간. 새 Context 상태(장보기 리스트) + 새 페이지 하나, 기존 `missing` 계산 로직 재사용 가능. 백엔드 불필요.
- **우선순위**: P1.

### E. 조리 모드 (단계별 체크리스트)

**시나리오**: 페르소나 A가 계란볶음밥을 처음 만들면서 레시피 상세 화면의 5단계 텍스트를 계속 위아래로 스크롤하며 확인합니다. 손에 기름이 묻어있거나 재료를 썰던 중이라 화면을 조작하기 번거롭고, 몇 번째 단계까지 했는지 헷갈리기 쉽습니다.

- **임팩트**: 현재 조리 순서는 정적 텍스트 나열뿐(`RecipeDetail.jsx` "상태: 없음")입니다. 단계를 체크하면서 진행하고 현재 단계를 큼직하게 보여주는 "조리 모드" 화면(선택적 진입, 강제 아님)은 요리 초보자인 페르소나 A에게 실질적인 사용성 개선입니다.
- **난이도**: 낮음~중간. `recipe.steps` 데이터는 이미 있으므로 새 데이터 없이 화면 상태(현재 단계 인덱스, 체크 여부)만 관리하면 됩니다. 타이머까지 넣으면 공수가 조금 늘지만 필수는 아닙니다.
- **우선순위**: P1.

### F. 유사 재료 대체 제안

**시나리오**: 페르소나 A가 만두전골 레시피를 보는데 "다진마늘 없음"이 뜹니다. 요리 경험이 적어서 "그냥 마늘을 다져 써도 되는지, 뭘로 대체 가능한지"를 스스로 판단하기 어렵고, 결국 그 레시피를 포기합니다.

- **임팩트**: 대파↔양파, 다진마늘↔마늘 같은 흔한 대체 관계를 정적 매핑 테이블로 만들어 "부족 재료" 옆에 "대신 양파를 써보세요" 힌트를 붙이면, 레시피를 포기하지 않고 지금 있는 재료로 시도하게 만드는 효과가 있습니다. 미션(낭비 방지)에도 간접적으로 기여합니다(재료를 사러 나가지 않아도 되므로).
- **난이도**: 중간. 코드 자체는 단순한 매핑 테이블 조회지만, 잘못된 대체 제안은 요리를 망칠 수 있어 데이터 큐레이션에 신중함이 필요합니다. 매핑 데이터 품질이 곧 기능 신뢰도이므로, 처음엔 기존 mock 레시피에 실제 등장하는 재료 범위(대파/양파/마늘/식용유 등) 안에서만 소규모로 시작하는 걸 권장합니다.
- **우선순위**: P2. 아이디어 자체의 가치는 있지만 데이터 큐레이션 부담 때문에 A~E보다 뒤에 둡니다.

## 4. 하지 않는 게 나은 것 (Won't do)

### G. 재료 수량/단위 관리 (개수 아닌 g/개/봉지 단위)

지금 재료 모델은 이름·보관구분·유통기한만 가지고 있고 수량 개념이 아예 없습니다(`mock.js` 참고). "정밀한 재고 관리"를 생각하면 자연스러운 다음 단계처럼 보이지만, 다음 이유로 지금 하지 않는 걸 권합니다.

- **레시피 매칭 로직 전체를 건드려야 함**: 지금 `getRecipeMatch`는 "있다/없다"만 비교합니다. 수량을 넣으려면 레시피 데이터에도 "계란 2개" 식으로 필요량을 넣어야 하고, "있긴 한데 부족한" 3번째 상태를 UI 전반(카드/상세/D-day 배지 위치)에 다시 설계해야 합니다. `docs/03`이 이제 막 확정한 용기(Vessel) 디자인도 폭/높이를 실루엣 종류로만 결정하는데, 여기에 수량까지 반영하려면 디자인 스펙을 또 한 번 갈아엎어야 합니다.
- **두 페르소나의 실제 불편과 거리가 있음**: 페르소나 A·B가 겪는 문제는 "정확히 몇 그램 남았는지 모른다"가 아니라 "뭐가 있는지/뭐가 곧 상하는지/뭘 또 샀는지"입니다. 가정식 레시피는 애초에 계량이 느슨해서("소금 약간") 정밀 수량이 추천 품질을 크게 높여주지도 않습니다.
- **투입 대비 효과가 낮음**: 큰 리팩터링 공수 대비, 사용자가 체감하는 개선은 "개수 표시가 조금 더 정확해진다" 정도입니다. 반면 A~E는 훨씬 적은 공수로 미션에 더 직접 기여합니다.

→ 나중에 "장보기 리스트(D)"가 실사용에서 자리를 잡고, 사용자들이 실제로 "몇 개 더 사야 하는지" 수량 단위 요청을 반복적으로 한다면 그때 재검토합니다. 지금 먼저 만드는 건 순서가 이르다고 판단합니다.

## 5. 로드맵

### 단기 — 백엔드 없이 프론트엔드만으로 가능 (지금 바로 시작 가능)

1. **A. 데이터 영속화** — 가장 먼저. 이후 항목들의 전제조건.
2. **B. 임박 재료 우선 추천 정렬** — A와 별개로 병행 가능, 공수가 거의 없음.
3. **E. 조리 모드**
4. **D. 부족 재료 기반 장보기 리스트**
5. **C. 소진/폐기 구분 + 낭비 리포트** — A 완료 후 착수.
6. **F. 유사 재료 대체 제안** — 데이터 큐레이션 여유가 생기면.

이 6개는 전부 `AppContext`/`localStorage`/정적 데이터 파일만으로 구현 가능하며, 현재 "백엔드 없는 프로토타입"이라는 제약과 충돌하지 않습니다.

### 중기 — 간단한 백엔드/영속 저장소가 필요해지는 시점

- **재료 자동 인식(바코드/영수증 스캔)**(기획서 P2): OCR·바코드 인식은 온디바이스로도 가능하지만, 인식 정확도를 위해 외부 API 연동을 고려하면 최소한의 프록시 서버가 필요해집니다. C(낭비 리포트)가 자리 잡아 "입력이 귀찮다"는 피드백이 쌓이면 그때 우선순위가 올라갈 항목입니다.
- **낭비 리포트(C)의 기기 간 확장**: 로컬스토리지는 기기 하나에 묶여 있습니다. 사용자가 "폰에서 입력한 게 PC에서도 보였으면"이라는 요청을 하기 시작하면, 이때부터 최소한의 서버+DB(계정 없이 기기 식별자만으로 동기화하는 가벼운 형태부터 검토)가 필요해집니다.

### 장기 — 계정/커뮤니티 등 플랫폼화

- **소셜 로그인/기기 간 완전 동기화**(기획서 P2): 정식 계정 시스템, 인증, 서버 DB.
- **커뮤니티 레시피 공유**(기획서 P2): 사용자 생성 콘텐츠 저장·검색·신고/모더레이션까지 포함하는 별도 서비스 영역. 계정 시스템(위 항목)이 선행되어야 의미가 있음.
- **F(대체 재료 제안)의 고도화**: 정적 매핑을 넘어 사용자들의 실제 대체 사용 데이터를 모아 추천을 정교화하는 단계. 계정·서버 데이터 축적이 전제.
