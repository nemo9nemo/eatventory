# 잇벤토리 (Eatventory) 기획서

## 1. 서비스 개요

- **한 줄 정의**: 집에 있는 식재료(실온/냉장/냉동)를 등록하면, 그 재료로 만들 수 있는 간단한 레시피를 추천해주는 반응형 웹 서비스
- **배경/문제의식**:
  - 식재료를 사놓고 방치하다 유통기한이 지나 버리는 경우가 많음 (음식물 낭비)
  - "오늘 뭐 해먹지?"를 매번 새로 검색하는 것이 번거로움
  - 재료를 기준으로 요리를 찾기보다, 레시피를 기준으로 재료를 사야 하는 기존 서비스들과 반대되는 접근이 필요함 ("있는 재료로" 먼저 시작)
- **서비스 형태**: 반응형 웹 (모바일/데스크톱 모두 대응, 별도 네이티브 앱 없음)

## 2. 타겟 사용자

- **페르소나 A — 자취생/1인 가구**: 요리 경험이 적고, 소량으로 산 재료를 다 못 쓰고 버리는 일이 잦음. 복잡한 레시피보다 "있는 재료로 빨리 뭐라도 해먹기"가 목표.
- **페르소나 B — 살림하는 2인 이상 가구**: 냉장고 재고 파악이 안 돼 같은 재료를 또 사거나, 유통기한을 넘겨 버리는 경우가 잦음. 재고 관리 자체에 대한 니즈가 있음.

## 3. 핵심 기능

| 기능 | 설명 | 우선순위 |
|---|---|---|
| 재료 저장소 (냉장고/선반) | 보유 재료를 실온/냉장/냉동 구분으로 등록·조회·삭제 | P0 |
| 재료 기반 레시피 추천 | 보유 재료를 기준으로 만들 수 있는 레시피를 매칭해 추천 | P0 |
| 레시피 상세 보기 | 재료 목록 + 간단한 단계별 조리 순서 제공 | P0 |
| 재료 검색/필터 | 저장된 재료를 카테고리·이름으로 검색 | P1 |
| 유통기한 표시/임박 알림 | 재료 등록 시 유통기한 입력, 임박 재료 하이라이트 | P1 |
| 레시피 즐겨찾기 | 자주 해먹는 레시피 저장 | P1 |
| 부족 재료 안내 | "이 재료만 더 있으면 만들 수 있어요" 형태의 추천 | P1 |
| 재료 자동 인식 (영수증/바코드) | 스캔으로 재료 자동 등록 | P2 |
| 소셜 로그인/기기 간 동기화 | 계정 기반 데이터 동기화 | P2 |
| 커뮤니티 레시피 공유 | 사용자가 직접 레시피 등록/공유 | P2 |

> 프로토타입은 P0 3개(재료 저장소, 레시피 추천, 레시피 상세) 중심으로 진행하고, 여유가 되면 P1의 검색/필터, 유통기한 하이라이트를 포함하는 것을 제안합니다.

## 4. 경쟁 서비스 분석

| 서비스명 | 강점 | 약점 | 우리와의 차별점 |
|---|---|---|---|
| 만개의레시피 | 방대한 레시피 DB, 검색 강력 | 재료 등록/재고 관리 기능 없음, 레시피 위주 탐색만 가능 | 보유 재료를 먼저 등록하고, 그 재료로 "만들 수 있는" 레시피만 좁혀서 추천 |
| 해먹남녀 | 감성적인 사진/콘텐츠, 초보자용 레시피 | 재료 재고 관리 기능 없음 | 냉장고/선반 UI로 재고를 시각적으로 관리하며 레시피와 연결 |
| Supercook (해외) | 재료 입력 → 레시피 매칭 컨셉이 유사 | 한식/국내 식재료·레시피 데이터 부족, UI가 오래됨 | 국내 식재료·레시피 기준, 실온/냉장/냉동 구분 저장이라는 실사용 맥락 반영 |

## 5. 가정 사항 (확인 필요)

기획서 작성 과정에서 아래와 같이 가정했습니다. 맞는지 확인 부탁드립니다.

1. 로그인/회원가입 없이 브라우저 로컬 저장(또는 프로토타입 단계에서는 더미 데이터)으로 우선 진행 — 계정 시스템은 P2로 후순위
2. 레시피 데이터는 자체 DB(더미/샘플)로 가정하고, 외부 레시피 API 연동은 이번 범위에 포함하지 않음
3. "간단히 따라 만들 수 있는 레시피"는 단계 수가 적고 조리 난이도가 낮은 레시피를 의미하는 것으로 해석
4. 언어/통화 등은 한국어/국내 사용자 기준
